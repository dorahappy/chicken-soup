# 吃饭了 Web 系统 PRD

版本：v0.1  
日期：2026-05-16  
状态：待产品验收

## 1. 背景

饭点前的核心问题不是“没有菜”，而是家庭或小团队在临近用餐时缺少一个明确、低摩擦的协作链路：

- 客户不知道今天能吃什么、多久能吃上、是否需要临时采购。
- 厨师需要同时管理菜单、材料、采购、备菜、烹饪进度和通知。
- 双方通常通过口头或聊天工具沟通，信息容易遗漏，进度也不透明。

“吃饭了”定位为面向家庭、小型工作室、宿舍、小餐桌场景的轻量用餐协作系统，先解决“今天吃什么、缺什么、做到哪了、什么时候吃”。

## 2. 目标

### 2.1 产品目标

1. 让客户在 30 秒内完成点单或表达想吃什么。
2. 让厨师在 1 分钟内判断本次订单需要采购哪些材料。
3. 让双方实时看到订单状态，减少重复催问。
4. 在饭菜完成时给客户明确的“吃饭啦”通知。

### 2.2 非目标

当前阶段不做完整外卖系统、支付、配送、库存财务、复杂会员营销、真实即时通讯。MVP 也不追求 AI 自动配餐，先把人和厨房的基础协作流程跑通。

## 3. 用户与场景

### 3.1 用户角色

| 角色 | 典型用户 | 核心诉求 |
| --- | --- | --- |
| 客户 | 家人、室友、同事、小饭桌成员 | 快速知道能点什么、预计多久吃、订单进度 |
| 厨师 | 做饭的人、家庭厨房负责人、小饭桌经营者 | 管理菜单、拆分材料、判断采购、推进制作 |

### 3.2 核心使用场景

1. 饭点前客户打开系统，浏览今日可点菜单。
2. 客户选择菜品，填写口味、人数或备注后提交订单。
3. 厨师收到新订单，系统汇总菜品材料，提示需要购买的材料。
4. 厨师确认采购/备菜/制作/完成等阶段。
5. 客户侧看到进度变化，完成后收到“吃饭啦”。

## 4. 竞品调研

调研日期：2026-05-16。竞品分为三类：餐食计划类、菜谱/采购清单类、餐厅厨房订单类。

| 产品 | 类型 | 可借鉴点 | 不适合直接照搬的点 |
| --- | --- | --- | --- |
| Mealime | 餐食计划 + 采购清单 | 快速选择餐食、自动生成购物清单、强调低决策成本 | 偏个人/家庭周计划，不强调厨师接单和实时制作状态 |
| Paprika | 菜谱管理 + 采购清单 | 菜谱结构化、材料清单可复用、适合沉淀个人菜单库 | 订单协作弱，用户需要自行组织流程 |
| Samsung Food / Whisk | 菜谱发现 + 计划 + 采购 | 菜谱到购物清单链路完整，免费功能覆盖较广 | 更偏内容平台，不适合小厨房内部接单协作 |
| AnyList / OurGroceries | 协作购物清单 | 多人协同采购体验清晰，清单心智简单 | 缺少菜品、订单和烹饪进度 |
| Toast / 餐厅 KDS | 餐厅点单与后厨看板 | 订单状态流、后厨任务看板、完成通知 | 面向商业餐厅，系统复杂度和成本明显高于本项目 |

### 4.1 关键结论

1. 用户真正要降低的是饭点决策成本，不只是维护菜谱。
2. 材料清单必须和菜品绑定，否则采购环节仍然靠人工回忆。
3. 厨师侧要优先呈现“新订单”和“本单缺什么”，而不是菜单编辑。
4. 客户侧不需要复杂功能，最重要的是可点、已点、做到哪了。
5. 本产品的差异化应落在“点单 -> 采购提示 -> 厨房进度 -> 吃饭通知”的闭环，而不是和大型菜谱 App 比内容量。

## 5. MVP 范围

### 5.1 必做功能

#### 登录与角色

- 用户进入系统后选择角色：客户、厨师。
- MVP 可使用演示身份，不做账号注册和密码。
- 不同角色进入不同工作台。

#### 厨师侧

- 菜品管理：新增、编辑、下架、删除菜品。
- 菜品字段：菜名、分类、图片/占位图、描述、材料清单、制作时长、难度、是否今日可点。
- 订单接收：查看客户提交的订单，按时间倒序展示。
- 采购提示：根据订单菜品材料生成本单采购清单。
- 订单推进：新订单、待采购、备菜中、烹饪中、已完成。
- 完成通知：订单完成后客户侧显示“吃饭啦”。

#### 客户侧

- 浏览今日可点菜单。
- 按分类筛选菜品。
- 查看每道菜的制作时长、难度、主要材料。
- 选择一个或多个菜品下单。
- 填写人数、口味偏好、备注。
- 查看订单状态与预计完成信息。
- 订单完成后看到明确提醒。

### 5.2 可选增强

- 常用菜一键复点。
- 按现有材料推荐可做菜品。
- 多客户同时点单合并采购清单。
- 菜品收藏与评价。
- 简单的厨房日历。

### 5.3 暂不做

- 支付、配送、退款。
- 真实用户体系和权限后台。
- 商业餐厅级 POS/KDS。
- AI 自动生成完整菜单。
- 多门店、多厨师排班。

## 6. 核心流程

### 6.1 客户点单流程

1. 进入客户端。
2. 浏览今日菜单。
3. 选择菜品。
4. 填写人数和备注。
5. 提交订单。
6. 查看订单进度。
7. 收到“吃饭啦”通知。

### 6.2 厨师处理流程

1. 进入厨师端。
2. 查看新订单。
3. 打开订单详情。
4. 查看系统汇总的采购清单。
5. 标记待采购/备菜中/烹饪中。
6. 完成订单。
7. 系统通知客户。

### 6.3 菜单维护流程

1. 厨师进入菜单管理。
2. 新增或编辑菜品。
3. 录入材料、制作时长、难度。
4. 设置是否今日可点。
5. 客户端菜单同步更新。

## 7. 信息架构

### 7.1 客户端

- 顶部：当前角色、切换角色入口。
- 菜单区：分类筛选、菜品列表、菜品详情。
- 订单区：当前订单、历史订单。
- 通知区：状态变化和完成提醒。

### 7.2 厨师端

- 概览：新订单数量、进行中订单、今日可点菜数量。
- 订单看板：按状态分组展示订单。
- 采购清单：按订单或按材料聚合。
- 菜单管理：菜品列表、编辑表单。

## 8. 数据模型

### 8.1 菜品 Dish

- id
- name
- category
- description
- image
- ingredients：材料名称、数量、单位、是否常备
- durationMinutes
- difficulty：简单、中等、复杂
- availableToday
- createdAt
- updatedAt

### 8.2 订单 Order

- id
- customerName
- dishes
- peopleCount
- note
- status
- shoppingList
- estimatedReadyAt
- createdAt
- updatedAt

### 8.3 状态枚举

- pending：新订单
- shopping：待采购
- preparing：备菜中
- cooking：烹饪中
- done：已完成
- cancelled：已取消

## 9. 验收标准

### 9.1 产品验收

1. PRD 明确产品定位、目标用户、核心流程和 MVP 范围。
2. 竞品调研能说明本产品差异化，不只是罗列功能。
3. 客户和厨师两端职责边界清晰。
4. 所有 MVP 功能都有对应场景和验收口径。
5. 暂不做内容明确，避免后续开发范围失控。

### 9.2 后续 UI 视觉稿验收

1. 必须覆盖客户首页、客户下单、客户订单进度、厨师订单看板、厨师采购清单、厨师菜单管理。
2. 视觉稿要体现饭点场景，避免通用后台模板感。
3. 移动端优先，桌面端兼容。
4. 信息层级要突出“今天吃什么”和“现在做到哪了”。

### 9.3 后续开发验收

1. 角色切换后展示正确工作台。
2. 厨师新增菜品后客户侧可见。
3. 客户提交订单后厨师侧即时出现。
4. 厨师侧能看到该订单的采购清单。
5. 厨师推进状态后客户侧能看到对应进度。
6. 订单完成后客户侧显示“吃饭啦”。

## 11. 待确认问题

1. 首版是否以移动端为主，桌面端为辅？
2. 客户是否需要实名，还是只填昵称即可？
3. 一单是否支持多个菜品？本 PRD 默认支持。
4. 采购清单是否需要区分“家里常备”和“需要购买”？本 PRD 默认需要区分。
5. 是否需要支持客户取消订单？本 PRD 数据模型预留，但 MVP 可先隐藏入口。
6. 菜品图片首版使用上传、外链还是默认占位图？
7. 是否需要多厨师协作？本 PRD 暂不纳入 MVP。
